# SHIPPED — EFD Merger: SPED Empresa + SPED Contábil

## Summary

Suporte a dois arquivos SPED por competência com merge de blocos configurável. O contador pode subir o SPED da empresa (gestão/estoque, com Bloco K) e o SPED do ERP contábil (com Blocos C/E corretos e Bloco G/CIAP), configurar qual bloco vem de qual arquivo, e gerar um Arquivo SPED merged que é parseado e vira o EFD ativo para toda a conferência fiscal.

**Extras entregues na mesma sessão:**
- `DELETE /efd-files/{id}` — excluir arquivo EFD com cascata completa
- `EditarEmpresaDialog` — edição do perfil fiscal da empresa (CIAP, Bloco K, inventário)

## What Was Built

### Backend
- `EfdFile.file_role` — `empresa | contabil | merged` com DEFAULT `merged` (zero breaking change)
- `services/efd_merger/merger.py` — motor principal portado do sped-merger.html (JS → Python): parse, index, validação CNPJ/período, montagem de blocos
- `services/efd_merger/dependency_resolver.py` — montagem do Bloco 0 mesclado: importa 0200/0190 (para Bloco K do Empresa) e 0300/0305/0500/0600 (para Bloco G do Empresa)
- `services/efd_merger/bloco9_calculator.py` — recalcula 9900/9990/9999 com contagem real
- `POST /fiscal-periods/{id}/efd-files/merge` — recebe dois file IDs + block_config, gera TXT merged, salva e roda `run_full_parse`
- `DELETE /efd-files/{id}` — remove arquivo + registros estruturados + validation runs + suggestions

### Frontend
- `MergerModal` na aba EFD: upload duplo, validação client-side de CNPJ/período, toggles de bloco por origem (Emp/Cont), log do resultado
- Badge de papel (SPED Empresa / SPED Contábil / Ativo) na lista de arquivos
- `EditarEmpresaDialog` — mesmos campos do cadastro, chama `PATCH /companies/{id}`
- Botão X (excluir) na lista de arquivos EFD com `confirm`

## Lessons Learned

### Técnico
- **Port JS → Python do motor de merge foi direto** — a lógica do HTML estava bem estruturada. A chave foi mapear `campos[N]` corretamente: campos em Python são `parts[1:-1]` (excluindo strings vazias iniciais e finais do split por `|`).
- **`file_role` com DEFAULT no banco** — a escolha de usar `server_default="merged"` na migration garantiu zero impacto nos arquivos já existentes. Sempre preferir DEFAULT ao invés de nullable para campos discriminadores.
- **`_clear_existing` já existia** — o delete endpoint ficou limpo porque o persist service já tinha toda a lógica de limpeza em cascata. Reutilizar em vez de reimplementar.
- **Validação de compatibilidade client-side** — ler o registro 0000 no browser antes de subir os arquivos evita round-trips desnecessários e dá feedback imediato ao usuário.

### Processo
- **Três features em uma sessão** — Merger, Delete e Edit empresa. As duas últimas foram quick fixes sem SDD, o que foi correto: são mudanças simples que não justificam o overhead do workflow completo.
- **Motor HTML como spec** — o sped-merger.html funcionou como especificação executável. A ferramenta que o usuário já usa em produção definiu exatamente o comportamento esperado.

### O que funcionou bem
- Testar mesclagem real logo após o build — o usuário confirmou que funcionou no mesmo dia
- Backend PATCH já existia — frontend só precisava do dialog
