# SHIPPED: NF-e XML Cross-check Engine

**Status:** ✅ Shipped

**Feature:** NFE_XML

---

## Resumo

Motor de cross-check entre XMLs de NF-e carregados e registros C100 do arquivo EFD. Compara valores monetários, status de situação, CST, chave de acesso e data de emissão. Inclui matching por chave primária e fallback por num_doc/série/modelo/emitente.

## O que foi entregue

| Componente | Descrição |
|-----------|-----------|
| `nfe_crosscheck/engine.py` | Orquestrador: match + regras + persist findings |
| `nfe_crosscheck/matcher.py` | MatchResult: matched_by_key, matched_by_fallback, orphans, ambiguous |
| `nfe_crosscheck/rules/entradas.py` | Regras de entrada: OMITIDA, ORFA, VL-DOC, VL-ICMS, VL-IPI, CST, DATA |
| `nfe_crosscheck/rules/saidas.py` | Regras de saída |
| `nfe_crosscheck/suggestion_mapper.py` | Geração de sugestões de correção CST |
| `ValidationRuleConfig` | Configuração por regra: ativa, severidade, CFOPs excluídos |

## Extensões entregues nesta sessão

- `is_ipi_contributor` na empresa — gate para `CONF-NFE-VL-IPI`
- `_resolve_c100_predominant_cfop` — resolve CFOP dominante via C190
- CFOP exclusões configuráveis (1556, 2556, 1407, 2407...) para ICMS/IPI
- Tela de parâmetros `/settings/validation-rules` — CRUD completo de configs

## Lições Aprendidas

**Técnico:** Para CFOPs de "uso e consumo" (1556 etc.), o ICMS consta no XML mas é 0 no EFD — necessário gate por CFOP dominante resolvido via C190, não via campo direto no C100.

**Técnico:** `ValidationRuleConfig` seedado via script Python após `create_all` — migration com INSERT falhou por tabela já existente (padrão do projeto).

**Processo:** Unificar CFOP exclusões + tela de parâmetros em um único modelo evita duplicação de lógica e facilita evolução futura.
