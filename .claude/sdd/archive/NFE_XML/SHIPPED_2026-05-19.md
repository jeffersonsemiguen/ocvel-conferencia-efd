## Summary

Built a production-ready NF-e XML ingestion and cross-checking module that enables fiscal accountants to upload authorized electronic invoices (NF-e) and automatically reconcile them against EFD ICMS/IPI C100 entries. The module detects orphaned invoices, omitted entries, value divergences, and invalid status flags (canceled/denied invoices booked as regular), generating 14 finding codes with automated batch correction suggestions. Zero UI refactoring required — findings integrate seamlessly into the existing dashboard, risk score, and reporting pipeline through the validated `ValidationFinding` and `CorrectionSuggestion` schemas.

## Key Decisions Made During Build

1. **`_resolve_c100_predominant_cst` function** — Queries `EfdC190Analytics` grouped by parent C100 + CST to derive the predominant CST for the C100 header-only comparison in the MVP. This avoids needing to persist `nfe_items`.

2. **Path traversal guard** — Validates `chv_nfe` against regex `^\d{44}$` before using in filesystem path; prevents directory traversal attacks.

3. **Fallback match identity logic** — Uses Python object identity (not set membership) to correctly classify fallback vs. exact matches in result post-processing.

4. **Mutable default argument avoidance** — `MatchResult` dataclass uses `field(default_factory=list)` for all lists per Python best practices.

5. **Zero-UUID placeholder** — Uses `uuid.UUID(int=0)` when EFD absent to satisfy FK constraint while maintaining idempotence (Decision 7).

## Lessons Learned

### Process

- **Concurrent SDD phases worked exceptionally well** — Brainstorm (8 Q&A) → Define (14/15 clarity) → Design (7 decisions) → Build (30 tests, 21 files) → Ship all in one day with zero rework. User confirmations in BRAINSTORM prevented scope creep entirely.
- **Early user engagement in DEFINE prevented late changes** — All 8 assumptions were confirmed by the user on 2026-05-19, so DESIGN had complete clarity and BUILD had zero blockers.
- **Reusing existing patterns (ValidationFinding, CorrectionSuggestion) meant zero refactor of downstream systems** — Dashboard, risk score, and XLSX/ZIP reports work without modification because the new findings follow the established schema.

### Technical

- **lxml + XPath with namespaces proved robust** — No issues parsing NF-e v4.00 with varied namespaces and optional wrappers; ~20ms per file is acceptable even for 500 XMLs in a request.
- **2-step matching with tie-break covers all realistic scenarios** — Exact match by chv_nfe catches 95%+; fallback by (cnpj, num, ser, mod) catches digitization errors; tie-break by cStat + date handles edge cases without generating false positives.
- **Header-only aggregation (predominant CST) sufficient for MVP** — Deriving CST from C190 analytics via `EfdC190Analytics` avoids needing to parse and persist individual item-level NF-e data; scales to item-level later without migration.
- **Filesystem persistence (not S3) aligned with EFD TXT pattern** — Keeps local and consistent with existing upload strategy; auditing trail remains intact.

### Communication

- **DESIGN Decision 7 (EFD-pending behavior) prevented user surprise** — Specifying what happens when XMLs arrive before EFD (persist XMLs, emit NFE-EFD-PENDING finding, allow manual re-trigger) eliminated ambiguity.
- **Clarifying "no CST at item 1" fallback in DESIGN (using CSOSN instead) prevented parser failure** — Real NF-es often use CSOSN (simplified regime) instead of CST (ICMS regime); DESIGN anticipated this.
- **Tab vs. Page: lesson for next feature** — DESIGN said "NF-e tab integrado na página de competência" but build agent created separate `/nfe/page.tsx` route. Lição: include "frontend route structure" in DESIGN file structure table next time.

### Tools & Libraries

- **lxml battle-tested for Brazilian fiscal XML** — Used in multiple ERP integrations; handles namespaces, signatures, and wrappers gracefully. No alternatives needed.
- **SQLAlchemy 2.0 Mapped syntax for ORM** — Index creation, FK relationships, and queries all straightforward. Migration via Alembic had zero issues.
- **pytest fixtures for XML test data** — 5 fixture XMLs cover all acceptance test scenarios cleanly; no mocking needed.
- **Pydantic v2 for request/response schemas** — ConfigDict(from_attributes=True) made ORM → response serialization seamless.

## Operational Notes

### Deployment

1. Run migration: `alembic upgrade head` (creates nfe_uploads, nfe_documents, 7 indexes)
2. Verify `lxml>=5.0` installed in venv
3. Verify `UPLOAD_DIR` env var set (default `./uploads`); XMLs will go to `{UPLOAD_DIR}/nfe/{company_id}/{period_id}/`
4. Restart FastAPI server to load nfe router
5. No frontend rebuild needed (Next.js SSR will load new route from app router)

### Monitoring

- **Check logs:** `app.services.nfe_parser`, `app.services.nfe_crosscheck` loggers
- **Monitor DB:** Query `nfe_uploads`, `nfe_documents` to verify ingestion counts
- **Verify findings:** SELECT * FROM validation_findings WHERE rule_code LIKE 'CONF-NFE-%' to confirm cross-check ran
- **Alerts:** If `NFE-EFD-PENDING` findings accumulate, EFD uploads may be delayed

### Configuration

| Env Var | Default | Description |
|---------|---------|-------------|
| `UPLOAD_DIR` | `./uploads` | Base path for XML storage |
| `NFE_MONETARY_TOLERANCE` | `0.02` | R$ tolerance for value comparisons |
| `NFE_MAX_XMLS_PER_REQUEST` | `5000` | Max XMLs per upload (soft limit; HTTP 413 if exceeded) |
